# Admin Portal Foundation — twominutes.in

This branch adds a **non-live, reviewable foundation** for the future admin portal. It does not change the existing public website or modify Cloudflare resources.

## Architecture decision

The production website is currently generated by `build.py` from `feed.atom`, then deployed with the existing GitHub Actions workflow to the Cloudflare Worker named `twominutes`. Keep that pipeline as the public site's build/deploy path.

The admin portal needs a separate authenticated API and private content workflow. Do not expose a GitHub token in browser code, do not accept arbitrary JavaScript as privileged server code, and do not make the existing public Worker private. Recommended production security boundary:

1. Protect the admin hostname/path using a dedicated Cloudflare Access application/policy restricted to the owner's verified email.
2. Place admin APIs behind authentication; verify Access identity at the Worker boundary and allow only the explicit admin identity.
3. Store drafts in a dedicated persistence layer (D1 is recommended; it is not currently present in the account as checked on 2026-10-20) and store the publishing credential as a Worker secret.
4. Publish by validating a draft and opening a GitHub change/commit on a controlled branch, then run the existing build and checks. Deploy only after successful validation.
5. Keep the public static website public. Do not enable account-wide Worker Access or change DNS/routes as part of this feature.

## Editor requirements

- Responsive admin-only dashboard.
- Draft, edit, preview, publish status, and error reporting.
- Article title, slug, categories/tags, summary/meta description, image URL/alt, publish date and body.
- Visual editor for ordinary writing.
- Code editor for HTML, CSS and JavaScript, with syntax highlighting and a preview mode.
- Distinguish **display code** (escaped code samples that never execute) from **interactive embed** (runs in a sandboxed iframe with a restrictive CSP, no same-origin privilege, and no direct access to admin cookies or APIs).
- Server-side validation for required fields, safe URL slug, content size, duplicate slug and untrusted HTML. Arbitrary inline script must never execute in the admin page itself.
- Preserve existing post paths unless the admin explicitly chooses and confirms a URL change. Never mass-rewrite existing Blogger posts.

## Analytics requirements

Use a dedicated analytics provider (evaluate Cloudflare Web Analytics first; GA4 optional if deeper reports are needed). Display provider-backed data only; never fabricate visitor counts. Suggested cards/reports: visitors, page views, top pages, referrers, daily trend, country/region where the provider supplies it, and engagement where available. City/region is approximate; do not collect exact GPS or unnecessary personal identifiers. Add clear privacy disclosure and consent/configuration review where required.

## Phased implementation

### Phase 0 — review (this PR)
Document the architecture and security boundary. No public-site changes or Cloudflare resource changes.

### Phase 1 — non-production UI prototype
Create an admin-only interface and mock data to test responsive layout and editor UX. No publishing API or real analytics yet.

### Phase 2 — authenticated infrastructure
Configure a dedicated Cloudflare Access app for the admin destination, a separate Worker/API and D1 storage. Review exact email allow-list and binding IDs before rollout. Do not bind admin APIs to the public site's unauthenticated routes.

### Phase 3 — drafts and publishing
Implement drafts and controlled publishing into the repository/build pipeline, with CSRF/authentication checks, server-side sanitization, branch-based changes and CI validation. Use secrets only in Worker/GitHub secret storage.

### Phase 4 — analytics
Connect a supported analytics data source and create a dashboard with clear data freshness/provider attribution.

### Phase 5 — staged verification
Test unauthenticated denial, allowed admin login, draft saving, HTML escaping, sandbox isolation, duplicate slugs, build failure/retry and preservation of existing URLs. Then request explicit permission before attaching a live hostname or enabling deployment.

## Constraints / decisions

- No Cloudflare API token, GitHub token, password, or private credential belongs in repository source.
- The existing public Worker must not be replaced as a shortcut for the admin API.
- No production deployment, DNS modification, Access policy change, or data migration is done by this foundation branch.
- AdSense approval is not guaranteed by an admin portal; content quality and applicable policies remain separate.
