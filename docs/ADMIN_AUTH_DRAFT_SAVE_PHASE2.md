# Admin Authentication & Draft Save — Phase 2 Proposal

This proposal is deliberately **not production-enabled**. It does not deploy a Worker, enable Cloudflare Access, change DNS, or attach a live hostname.

## Required architecture (no public-site disruption)
1. Keep the public Worker `twominutes` and its existing routes public as they are now.
2. Create an **independent** admin hostname and dedicated Cloudflare Access application for that hostname only, with default-deny behavior and one explicit email Include rule for `shashank77a@gmail.com`. Do not create an account-wide or wildcard Access policy.
3. Create a separate Admin API Worker and D1 database. Keep all content APIs behind Access and independently verify the Access identity at the API boundary; reject requests whose verified identity does not match the configured admin email.
4. Keep drafts in D1 with server-generated IDs, timestamps, status, and safe slug uniqueness constraints. Never accept arbitrary repository credentials from the browser.
5. Publishing must be a separate reviewed action: validate draft fields, preserve existing post URLs by default, update `feed.atom` via a controlled GitHub branch/PR, run existing validation/build checks, then deploy only after successful checks and explicit approval.
6. All GitHub and other credentials must live in GitHub Actions secrets or Worker secrets, never in browser JavaScript or committed source.
7. HTML/CSS/JS examples are escaped for display by default. Interactive embeds, if later supported, must execute only in a restrictive sandboxed iframe and never in the admin origin.

## Draft schema (proposal only)
- `id`: random UUID generated by server
- `title`: required, trimmed, reasonable maximum length
- `slug`: required, normalized, unique; no slash traversal or reserved paths
- `summary`: optional, length-limited
- `body_html`: draft body, sanitized on rendering/publishing
- `status`: `draft` or `ready_for_review`; publishing is a distinct privileged state transition
- `created_at`, `updated_at`: server timestamps

Use parameterized SQL statements. Validate all inputs server-side. Enforce request size limits, same-origin/CORS restrictions, appropriate method checks, and no-store headers for private responses. Do not mistake a client-supplied email/header for a verified Access identity.

## Manual prerequisite
Before creating an Access application, check that the Zero Trust incident is resolved and that Access API reads are consistently healthy. Re-read the team domain and application/policy list first. The public website Worker and root/www DNS must not be changed.

## Acceptance tests before deployment
- Unauthenticated visitor cannot load admin UI/API.
- Wrong authenticated email is denied.
- `shashank77a@gmail.com` can authenticate successfully.
- Draft create/update/read works and survives reload.
- HTML is escaped/sanitized; script cannot run in admin origin.
- Duplicate or invalid slug rejected.
- Existing public URLs and homepage remain unchanged.
- No production hostname/DNS/Worker deployment occurs during staging setup.
